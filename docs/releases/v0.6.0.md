# v0.6.0 — Shizzi and Shizuku consolidation

## One app for tethering and its helper

This release brings the required parts of Shizuku into Shizzi. Users no longer need a separate Shizuku app to grant access or start the tethering helper. One Shizzi app can remain pinned or locked in Recents.

The included privileged helper is a separate process that uses Android's shell permissions. It performs Shizzi's tethering operations. Android still requires debugging authorization before that process can start.

New setup actions live inside Shizzi:

- Pair Shizzi with Android's wireless debugging through its own pairing code and port fields.
- Start the helper through an existing pairing.
- Copy a USB startup command for an authorized computer.
- Start protection, stop tethering, or stop tethering and all protection.

Shizzi stores its own encrypted pairing credentials. It does not import credentials from Shizuku. Initial pairing can use split screen to keep Android's pairing dialog visible beside Shizzi.

## Protection and recovery controls

Open **Settings → Protection and recovery**. Sixteen controls replace the earlier session-only keep-alive setting. Existing opt-outs from keeping the CPU awake during sessions survive the upgrade.

App-level protection defaults to maximum persistence. Controls that change the whole phone remain individually disabled.

| Control | Default | What it does |
|---|---|---|
| Protect while idle | On | Keeps the protection service available when no tethering session is active. An ongoing notification remains visible. |
| Keep CPU awake during sessions | On | Holds a wake lock while starting, sharing, or recovering. This keeps the CPU awake with the screen off and uses more battery. |
| Keep CPU awake while idle | On | Extends the wake lock while idle protection is enabled. This can use substantial battery without tethering. |
| Recover the helper automatically | On | Uses Shizzi's existing pairing to restart a dead helper through wireless debugging. |
| Resume interrupted tethering | On | Restarts a previously requested session after helper recovery. A deliberate Stop cancels resumption. |
| Start protection after reboot | On | Attempts to start protection after the first unlock, when protected credentials become available. Android may require opening Shizzi. |
| Resume tethering after reboot | On | Resumes the saved session request after unlocking, when protection and recovery are available. |
| Check the helper every | 5 seconds | Offers 2, 5, 10, or 30 seconds. Binder death, which signals that the helper process ended, triggers an immediate check. |
| Recovery attempt limit | Unlimited | Offers 3 attempts, 10 attempts, or unlimited attempts. Finite limits pause recovery for user attention. |
| Retry quickly after a failure | On | Uses delays of 2, 5, 15, 30, then 60 seconds. Turning it off uses 15, 30, 60, then 120 seconds. Each schedule repeats its final delay. |
| Keep the screen on | Off | Prevents screen timeout while Shizzi is visible. It uses more battery and does not bypass the lock screen. |
| Restore wireless debugging | Off | Re-enables debugging when recovery needs it, if Shizzi has permission to change secure settings. It still needs a real Wi-Fi connection. |
| Prevent debugging authorization expiry | Off | Changes the phone's debugging authorization timeout. Previously authorized debugging devices remain trusted until authorization is revoked. |
| Stabilize USB with No data transfer | Off | Applies the tested USB mode workaround. Changing USB mode can interrupt debugging and file transfer. Stop tethering before changing it. |
| Disable light idle | Off | Disables Android's lighter idle restrictions while protection runs. It affects all apps and can increase battery use. |
| Disable deep idle | Off | Disables Android's deeper idle restrictions while protection runs. It affects all apps and can increase battery use. |

Each phone-wide control requires individual enablement. Shizzi checks whether Android supports the requested change and reports failures. It saves original values before applying changes and attempts restoration when controls are disabled or protection ends.

Restoration preserves changes made outside Shizzi. If restoration cannot finish, the saved record remains available for another attempt. USB stabilization requires USB tethering to be set to Never.

## Recovery, cleanup, and startup fixes

- A native starter detaches the helper before Java starts. This fixes startup through the wireless debugging shell.
- Each recovery attempt has a fifteen-second deadline. Blocked connections close when the attempt expires.
- An attempt timing out no longer terminates the protection worker. External cancellation still stops it.
- Shizzi saves the requested session state. Stop clears that request before cleanup, so recovery cannot silently restart sharing.
- Shizzi records the tethering types it starts before requesting them from Android. A replacement helper reconciles those records before starting a new session.
- A fresh helper no longer erases ownership records merely because its in-memory session is empty.
- Recovery uses shell attribution for Android's tethering operations. This fixes cleanup requests that Android previously attributed to its own package.
- Manual Start uses its own service action, so it works even when automatic session resumption is disabled.
- The provider accepts helper publication only from Android's shell. The helper accepts privileged calls only from Shizzi's installed UID.

The existing watchdog continues checking whether tethered traffic uses the intended upstream connection. If cleanup cannot be confirmed, Shizzi reports that the hotspot may remain on.

## Setup and limits

Stop any session or hotspot left by an older build before the first standalone session. Older builds did not create the ownership record needed for recovery.

Wireless recovery needs a real Wi-Fi connection, valid pairing credentials, and wireless debugging enabled. The hotspot alone is insufficient. An existing helper can continue while using mobile data, but mobile-data-only operation cannot provide this wireless recovery path.

USB startup and USB tethering are separate features. An authorized computer can start the helper over USB. On the tested Samsung A17, enabling USB tethering restarted Android Debug Bridge (`adbd`) and killed shell processes. The tested stable configuration used Wi-Fi tethering with USB tethering set to Never.

The optional Restore wireless debugging control was not enabled during the recorded recovery test. Recovery after Android disables wireless debugging, reboot recovery, and restoration of every phone-wide setting remain unverified on the A17.

## Recorded validation

Development checks passed before this release preparation:

- 180 unit tests passed.
- Debug and release builds passed.
- Lint reported no errors and 78 warnings.
- All five packaged native files had 16 KB alignment.
- Wireless pairing succeeded with Shizzi's own credentials.
- After a forced helper death, Shizzi restarted it wirelessly and resumed tethering in about eight seconds.
- Stop during wireless recovery kept tethering off.
- Short screen-off checks passed with Shizuku's app and server stopped.
- USB disconnection left the same helper and tunnel running.
- The user reported internet access from a Mac through the A17 hotspot after switching to Dark Star.

These are bounded checks. Extended screen-off operation on Dark Star and thirty-minute endurance remain unverified.
