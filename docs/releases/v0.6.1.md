# v0.6.1 — Datapath speed tuning

This release changes only the userspace datapath, which carries tethered client traffic. The app, helper, and protection controls are unchanged from v0.6.0.

None of these changes has been measured on a phone. Each one either can make traffic faster or, at worst, has no effect. No change limits speed.

## Speed changes

| Change | Before | After | Why it can help |
|---|---|---|---|
| GRO on the TUN | Off | On | GRO (generic receive offload) merges consecutive TCP segments of one flow into one larger packet before the TCP layer processes it. Fast client uploads then cost fewer trips through the stack. GRO checks checksums before it merges, so it accepts nothing the stack would reject. |
| Congestion control on the client leg | Reno | CUBIC | CUBIC regrows its sending window faster after a lost packet, which can help on a lossy Wi-Fi link. The upstream leg uses Android's kernel TCP and does not change. |
| TCP copy buffer | 32 KiB | 64 KiB, pooled | Each read and write moves more bytes, so a fast transfer makes fewer system calls. A pool reuses the buffers between connections. |
| UDP socket buffers | About 208 KiB | 2 MiB requested | A fast QUIC burst can overflow a small buffer, and an overflow drops datagrams. Android caps the request at its own maximum. |
| TCP connections being set up at once | 512 | 2048 | A connection counts toward this limit until its upstream dial finishes, which can take 10 seconds. A client that opens many connections to dead hosts, such as a torrent client, could fill the old limit and delay every new connection. |

## UDP fixes

These fixes help QUIC (HTTP/3), games, and streaming over UDP.

- **Both directions now share one idle timer.** Before, each direction of a UDP flow timed out on its own after 60 seconds. A one-way stream, where the client never replies, was closed while data was still arriving. Now traffic in either direction keeps the flow alive.
- **A failed write drops one datagram, not the flow.** Before, any write error closed the whole flow. The next datagram then opened a new flow with a new upstream port, and QUIC had to treat that as a change of address. Now a flow ends only after 16 errors in a row.

## Considered but not changed

- **Batched TUN reads and GSO.** gVisor uses these only on socket file descriptors. A TUN is not a socket, so these options would do nothing.
- **Skipping checksum checks on incoming packets.** This would save a little CPU. But a corrupted packet would then reach the destination, where today the netstack drops it and the client resends. That can be worse than no change.
- **Larger TCP buffers.** The client-facing leg has a round-trip time of a few milliseconds. The existing 4 MiB maximum already allows several gigabits per second at that delay.
- **Less frequent garbage collection.** This could save CPU, but the helper would use more memory. If Android then kills the helper, the session stops.

## Recorded validation

These checks ran in a cloud container, not on a phone:

- The Go datapath tests passed with the race detector, and the new UDP and copy tests passed 5 runs in a row.
- `go vet` passed for Android arm64 with the NDK compiler.
- 180 unit tests passed.
- Debug and release builds passed.
- Lint reported no errors and 77 warnings. v0.6.0 recorded 78.
- All five packaged native files had 16 KB alignment.

Throughput, QUIC behavior, and battery use on a real phone remain unverified.

## Release contents

This release contains two APKs. Both report versionName `0.6.1-standalone` and versionCode `9`.

| File | Build | Signed with |
|---|---|---|
| `shizzi-unified-v0.6.1-release.apk` | Release: shrunk by R8, not debuggable | The new Shizzi release key |
| `shizzi-unified-v0.6.1-debug.apk` | Debug, like the v0.6.0 APK | A cloud container's debug key |

Use the release APK. It is the first APK signed with Shizzi's own release key, and every later release will use the same key. As a result, later releases can update it in place.

The release key's certificate SHA-256 fingerprint is:

```
30:5B:B4:83:AF:66:8D:12:02:63:9D:4B:31:55:C1:C0:2F:3D:D1:36:F4:5F:E5:E8:A3:91:01:2B:51:F7:31:7C
```

Neither APK can update an existing v0.6.0 install, because v0.6.0 was signed with a different debug key. Android does not install an update signed with a different key. To install v0.6.1, uninstall v0.6.0 first. Uninstalling removes Shizzi's saved pairing, so pair again afterwards.

The release build passed the same build checks as the debug build. It has not been run on a phone. R8 can remove code that is reached only through reflection, so check pairing, helper startup, and tethering after you install it.
